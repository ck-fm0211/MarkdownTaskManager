# task-history-explorer

## 目的・位置づけ

カテゴリ・タグ・TASK-ID・期間からチケットの履歴や背景を調べ、チャットにレポートを返すスキルの SSOT。
運用データと Git は**読み取り専用**で扱い、タスクの編集・移動・アーカイブや Git の変更は行わない。
利用者が明示的に保存を依頼した場合だけ、開発リポジトリの `docs/history/` に新しい文書を作る。

タスク形式は [AI_WORKFLOW.md](../../../AI_WORKFLOW.md)、フォルダーの役割と公開情報の制約は
[AGENTS.md](../../../AGENTS.md) に従う。Markdown データキーやファイル名は翻訳しない。
実在しない連携・スキルを「ある」「利用できる」と説明しない。

## 対象の選択（共通 SSOT に委譲）

受け付ける入力軸は **category / tag / TASK-ID / 期間**。
対象フォルダーの確認、grep による候補抽出、多選択、明示的な確定までの工程は
[_shared-task-selection.md](_shared-task-selection.md) に従い、本書では重複して定義しない。
以降は共通手順から受け取った、確定済み TASK-ID と所在の一覧を使う。

## 読み込み（データと Git）

- `npm run tasks -- where` で確認した `dataDir`（利用者が別途指定した場合はそのフォルダー）の
  `kanban.md` と `archive.md` を対象にする。リポジトリ直下と `examples/` はダミーデータなので代用しない。
- 確定した各 ID について、共通 SSOT の grep / sed の用法で所在を確認し、**ブロック全文**を読む。
  メタデータだけでなく説明、サブタスク、`**Notes**:` 以降も根拠として確認する。

```bash
# データフォルダーで実行する例。TASK-042 は確定した ID に置き換える
grep -n "^### TASK-042 " kanban.md
sed -n '/^### TASK-042 /,/^### TASK-/p' kanban.md
grep -n "^### TASK-042 " archive.md
sed -n '/^### TASK-042 /,/^### TASK-/p' archive.md
```

範囲末尾に含まれる次のタスク見出しは対象から除く。同じ ID が両ファイルにある場合は、
共通 SSOT の確認結果に従い、内容を黙って統合しない。

関連する Git リポジトリでは、共通 SSOT の用法で TASK-ID に言及するコミットと
関連ファイルの履歴を確認する。複数 ID はそれぞれ調べる。

```bash
git log --oneline --extended-regexp --grep='TASK-042([^0-9]|$)'
git log --oneline -- <path>
git show <commit> -- <path>
```

`<path>` はタスクの記述や差分から確認した関連ファイル、`<commit>` は見つかったコミットに置き換える。
データ自体が Git 管理されていれば、そのファイル履歴も読む。Git 管理外ならデータの変更履歴は
取得できないと明記し、開発リポジトリのコミット・ソース履歴を調べる。サンプルの履歴で補わない。
コミット日時とタスクの日付は区別し、ID の言及だけで関連性を断定せず差分で裏付ける。

## レポート（チャット）

まず検索条件・確定した ID と所在・参照した履歴の範囲を短く示す。
各チケットについて、次を整理する。

- **状態 / カテゴリ / タグ / 日付**: `**Status**`、`**Category**`、`**Tags**`、
  `**Created**` / `**Started**` / `**Due**` / `**Finished**` など。空欄は「未設定」とする。
- **経緯の要約**: 背景、判断、実施内容、結果。ブロックや `**Notes**:` の根拠を示す。
- **関連コミット**: ハッシュ・件名・日時と、そのチケットとの関係。見つからなければ「確認できず」。
- **関連ファイル**: パスと役割、根拠となるタスク記述またはコミット。
- **学び**: 再利用できる知見と注意点。記録された事実と推測を分け、不明点を明記する。

最後に、選択した全チケットを横断する**時系列と総括**を示す。
日付・TASK-ID・出来事・根拠を対応させ、共通する課題、判断の変化、残る疑問をまとめる。
記録のない因果関係や日付は補完しない。

## 保存（任意）

**利用者が明示的に保存を依頼したときだけ**、チャットのレポートを次の新規文書に保存する。

```text
docs/history/<category>/YYYY-MM-DD-<topic>.md
```

- 保存先は開発リポジトリ内。必要なディレクトリを作る。
- `<category>` はタスクの `**Category**` を slug にする。日本語はそのまま、空白は `-`、
  ASCII 英字は小文字にする（例: `Backend API` → `backend-api`、`経理` → `経理`）。
  パス区切り文字は `-` に置換する。複数カテゴリや未設定で保存先が定まらない場合は利用者に確認する。
- `YYYY-MM-DD` は保存当日のローカル日付。`<topic>` は内容を表す短い kebab-case または underscore の語句。
- **新しい文書ファイルだけ**を書き、既存レポートは上書きしない。同名なら別の topic を使う。
  `kanban.md` / `archive.md` は一切編集しない。
- UTF-8（BOM なし）、NUL なしで保存する。コミット対象の文書には実パス・個人名・会社名・実業務データ・
  認証情報を含めず、必要な内容は匿名化する。保存後は作成したパスをチャットで知らせる。

## 手動 dry-run 例（架空データ・実ファイルへの保存なし）

入力軸: category=`Backend`、tag=`#bug`、期間=`2026-01-01`〜`2026-01-31`、対象日付=`Finished`。
選択は共通 SSOT に委譲し、その手順で利用者が確定した結果を受け取る:

```text
TASK-042 | kanban.md
TASK-039 | archive.md
```

上の読み込み例を両 ID に適用し、現役・アーカイブのブロック全文を読む。
Git も各 ID の `git log --grep`、関連ファイルの `git log --oneline -- <path>`、
必要な `git show` を確認する。以下はブロックと差分が一致したと仮定したチャット例で、
コミット・パスも架空。

> 対象: Backend / #bug / Finished が2026年1月の2件。データは Git 管理外のため、データの変更履歴は取得できず。
>
> **TASK-039 — 再試行処理を修正**（archive.md）  
> 状態: done / カテゴリ: Backend / タグ: #bug #retry / Created: 2026-01-05、Finished: 2026-01-12（他の日付は未設定）。  
> 経緯: Notes に再試行上限の導入を記録。関連コミット: `a1b2c3d`（2026-01-12）`fix: Limit retries (TASK-039)`。  
> 関連ファイル: `src/retry.js`（再試行制御。コミット差分で確認）。学び: 再試行上限を明示する。
>
> **TASK-042 — 通知の重複を修正**（kanban.md）  
> 状態: done / カテゴリ: Backend / タグ: #bug / Created: 2026-01-15、Finished: 2026-01-20（他の日付は未設定）。  
> 経緯: Notes に通知IDによる重複排除を記録。関連コミット: `d4e5f6a`（2026-01-20）`fix: Deduplicate notifications (TASK-042)`。  
> 関連ファイル: `src/notifications.js`（通知処理。コミット差分で確認）。学び: 同じ通知を再処理しても結果が重複しない設計にする。
>
> **横断時系列・総括**: 1月12日 TASK-039 で再試行上限を導入（Notes と `a1b2c3d`）、
> 1月20日 TASK-042 で重複排除を導入（Notes と `d4e5f6a`）。両件は再実行時の挙動に関わる。
> 直接の依存関係は記録から確認できず、追加調査の余地がある。

ここで終了すればチャットのみ。続いて利用者が「このレポートを保存して」と依頼した場合だけ、
保存当日が `2026-11-23` なら `docs/history/backend/2026-11-23-retry-history.md` を新規作成する。
